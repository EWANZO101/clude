PART 4 — DONE (this zip)
---------------------------
- agent/health_check.py — a real functional health check, replacing Part
  3's "process is still alive" stand-in (spec Sections 28-32):
  - kiosk_health_check_url -> real HTTP GET, 2xx/3xx = healthy
  - kiosk_health_check_command -> real subprocess, exit 0 = healthy
  - neither configured -> honest fallback to process-liveness only (the
    Kiosk Application still doesn't exist as a real project to point a
    real check at, so this stays usable either way)
  - structural check (files on disk) runs once, un-retried, before the
    functional check — a missing/empty app dir is a hard failure
  - retries the functional check within a short budget so a just-restarted
    process isn't judged unhealthy for needing a moment to start
  - a "healthy" response is distrusted if the ProcessSupervisor says the
    process it's supposedly checking has actually died
- agent/update_manager.py — spec Section 29's full automatic-rollback flow
  is wired for real now: failed health_check -> reports rolling_back ->
  agent.recovery.restore_recovery_point() (Part 2's already-proven
  mechanism) -> restart the configured supervisor onto the restored files
  -> RE-CHECK health on the restored version -> only then report
  rolled_back. If the restore itself can't run, or the restored version
  also fails its health check, this reports failed plainly rather than
  claiming a rollback that didn't actually leave things working.
- Status reporting is now wrapped (_report_status_safe) so a reporting
  hiccup — including the Admin Panel not yet recognizing the new
  rolling_back/rolled_back status values, which this project has no way to
  verify from its own side this time (see below) — can never block the
  actual local rollback action from happening.
- New settings: kiosk_health_check_url, kiosk_health_check_command,
  health_check_timeout_seconds, health_check_retries,
  health_check_retry_delay_seconds, health_check_grace_period_seconds — all
  optional, all defaulted, so an Agent with none of these set behaves
  exactly like Part 3 (structural + process-liveness only).
- Tested for real, no mocking, for everything local to this machine:
  tests/test_health_check.py (17 tests) against a real backgrounded HTTP
  server toggled healthy/unhealthy mid-test, real subprocesses for the
  command-check path, and a real ProcessSupervisor; tests/
  test_rollback_integration.py (4 tests) builds real update packages, runs
  them through the real validator/recovery/installer machinery, supervises
  real subprocess "kiosk" stand-ins (tiny real HTTP servers that serve 200,
  serve 500, or crash on startup), and proves the full restarting ->
  health_check -> rolling_back -> rolled_back (or failed) sequence
  end-to-end — including a real HTTP request after rollback confirming the
  process actually answering is genuinely the restored version, not just
  "install said it worked."

TESTING GAP — FLAGGED HONESTLY, READ THIS ONE
--------------------------------------------------
Parts 1-3 were integration-tested against the real Admin Panel, checked
out and running as an actual HTTP server, in that build environment. This
build environment does NOT have the Admin Panel project available to run.
tests/test_rollback_integration.py therefore uses a scripted stand-in
client (_FakeAdminPanelClient) instead of a real server — everything LOCAL
(recovery restore, install, process supervision, real HTTP health checks
against real running processes) is still fully real and tested, but the
actual wire round-trip to the Admin Panel, and specifically whether it
accepts the two new status values this part introduces (rolling_back,
rolled_back), has NOT been verified against the real Admin Panel this
time. This should get a real end-to-end pass against the actual Admin
Panel before being trusted in production — called out here rather than
left implicit.

SETUP REMINDER
-----------------
See README.md. To exercise the new health check for real, set either
kiosk_health_check_url (e.g. http://127.0.0.1:PORT/health) or
kiosk_health_check_command in settings.json alongside kiosk_start_command
— any long-running process that answers that check is enough to see the
full restarting -> health_check -> successful (or -> rolling_back ->
rolled_back) flow run end to end. tests/test_rollback_integration.py is a
good example of exactly this, using a tiny real Python HTTP server as the
stand-in Kiosk Application.
