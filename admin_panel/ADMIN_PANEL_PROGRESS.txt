RELEASES FIX (this update): auto-fix version + safe delete
------------------------------------------------------------------
Directly prompted by the real v3.1 incident: a package was uploaded with
the wrong version typed into the form (its own update.json said something
different), and the only way to fix it was rebuilding and re-uploading the
whole ZIP. This update, adopted from an improved version of the releases
feature you provided:
- `UpdatePackage.delete_blocking_reason()` — a package is only safe to hard-
  delete if nothing points at it: no deployment history, and no instance
  currently reporting it as its running or Last-Known-Good version.
  Otherwise, delete is refused with a clear explanation and Withdraw is
  suggested instead (which keeps history intact but stops further pushes).
- `peek_manifest_version()` — reads the version actually baked into a
  package's own update.json, independent of what was typed on the upload
  form
- New route `/admin/releases/<id>/autofix-version` — for an invalid
  package, re-validates against its own manifest's version instead of the
  wrong one from the form, refusing if that version already exists as a
  different package (conflict) or if the manifest version already matched
  (meaning the mismatch wasn't the actual problem)
- New route `/admin/releases/<id>/delete` — hard delete, gated by the
  guard above; the Delete button only appears in the UI for packages that
  are actually safe to remove

Verified for real, not just adopted on faith: uploaded a package with a
deliberate form/manifest version mismatch, confirmed it was marked invalid,
ran auto-fix, confirmed the version corrected and the package became
validated; confirmed auto-fix correctly refuses when the target version
already exists as a separate package; confirmed an unused package can be
deleted (row and file both actually removed) and its Delete button appears;
then pushed a package to a real instance and confirmed delete on that same
package is now correctly refused, with the Delete button no longer shown at
all in the list.

CLIENT PORTAL (this update): a second, separate login system
------------------------------------------------------------------
Follow-up correction to the "Client Portal" work above — that gave the
existing "operator" COMPANY role the right capabilities, but what was
actually wanted was a genuinely separate system: a client signs themselves
up (no company, no invite), and only after that does a platform admin
assign them to whichever specific instance(s) they should operate —
possibly across different companies, since a client isn't scoped to one.

- New models: `ClientUser` (own email/password, own login, no
  CompanyMembership — see models.py's "Client Portal" section for the full
  rationale), `ClientInstanceAccess` (the assignment: one client, one
  instance, who granted it), `ClientActionLog` (a self-contained activity
  trail, since AuditLogEntry's actor_id is a NOT NULL FK into `users`, not
  `client_users`). Also `User.is_service_account` + a lazily-created
  synthetic "Client Portal" User row: several existing tables
  (InstanceCommand.requested_by_id, UpdateDeployment.requested_by_id) have
  NOT NULL foreign keys into `users.id` — a ClientUser's own id must never
  be written there (different table, colliding id space), so those writes
  use the service account's id while a duck-typed shim object still carries
  the real client's email into the human-readable log text, and
  ClientActionLog captures full attribution separately.
- Flask-Login now serves two account types off one session mechanism:
  `ClientUser.get_id()` returns `"client:<public_id>"`, `User.get_id()`
  stays a bare public_id (so already-logged-in staff sessions weren't
  invalidated), and the shared user_loader in app/__init__.py dispatches on
  that prefix.
- New `app/blueprints/client_portal.py` (url_prefix `/client`): signup,
  login, logout, a dashboard listing only the instances that client is
  assigned to, and an instance page reusing the same start/stop/restart +
  Items & Tools + Local Kiosk Users + push-an-update capabilities as the
  operator company role, permission-checked via ClientInstanceAccess
  instead of a company role. Deliberately does not extend base.html — a
  standalone `client_portal/_base.html` shell, same visual language, no
  Platform/Company nav (none of it applies).
- New `Platform → Clients` pages (platform.py + templates/platform/
  clients.html, client_detail.html): list every ClientUser, open one to see
  their assigned instances + recent activity, assign a new instance (a
  single dropdown across every company's instances), revoke, disable.
- Found and fixed a real gap while testing: several staff-only decorators
  (rbac.py's load_company_context, platform_auth.py's
  platform_admin_required) called methods that only exist on `User`
  (role_in, is_platform_admin) — a logged-in ClientUser hitting any of
  those routes 500'd instead of being turned away. Fixed at both layers:
  a new before_request hook (confine_client_portal_sessions in
  app/__init__.py) redirects a logged-in ClientUser to their own dashboard
  before any staff route runs at all, and the two decorators themselves now
  use getattr(...) fallbacks as defense in depth.
- Migration a8d3f6b21e0c (chained after f2a6c3e91d47, applied directly
  against the live sqlite file the same way, then stamped — see that

REAL KIOSK APP INVENTORY SYNC (this update)
------------------------------------------------------------------
Follow-up to the Client Portal work above — "Items & Tools" and "Local
Kiosk Users" turned out to be simplified Admin-Panel-only placeholders
with no connection at all to kiosk_app's own real Item/Tool/LocalUser
tables (a genuine stock/consumable/PPE inventory system with quantity,
SKU, checkout/maintenance history — nothing like the Admin Panel's
"scanners/printers" asset list). Built the real two-way sync:

- kiosk_app/app/models.py: added `public_id` (stable cross-system
  identity) and `updated_at` to Item, Tool, LocalUser, plus `deleted_at`
  tombstones on Item/Tool (LocalUser has no delete concept in this app at
  all — see admin.py — so a remote "removed" maps onto is_active=False
  here instead of a tombstone). `to_sync_dict()` on each. Since release
  packages ship with no migrations/ folder (see run.py's own docstring),
  added a small in-place "poor man's migration" (run.py's
  `_ensure_sync_columns()`) that ALTER TABLEs in any missing column on
  every startup — a no-op once already applied, same spirit as
  `db.create_all()` itself.
- New kiosk_app/app/blueprints/sync_api.py: GET /api/sync/state and POST
  /api/sync/apply, deliberately unauthenticated like the existing /health
  route — this process binds to 127.0.0.1 only (run.py), so only another
  process on this exact machine (in practice, only the Agent) can ever
  reach it. Last-write-wins by updated_at, decided independently per row.
- Admin Panel: InstanceEquipmentItem gained sku/quantity/unit/category/
  unit_cost (kind="item"), tool_status/checked_out_by_name/
  current_project/purchase_price (kind="tool"), barcode_code (either
  kind, kiosk-assigned, never set from this side), and deleted_at.
  InstanceLocalUser gained username/role/badge_code and deleted_at. New
  agent_api.py endpoints (GET/POST .../equipment/sync,
  .../local-users/sync) mirroring kiosk_app's sync_api.py exactly —
  same last-write-wins-by-updated_at logic, independently on this side.
  Every existing list/export/backup query updated to filter
  deleted_at IS NULL; every existing "Remove" button now soft-deletes
  instead of hard-deleting (a hard delete would just look like "never
  existed" to whichever side hasn't synced since, which would re-create
  it right back). Migration c4e91b7a3f52.
- New Agent module agent/inventory_sync.py (5th polling thread in
  main.py, alongside heartbeat/config/update/command): each pass, fetch
  both sides' current full state (Admin Panel via the new ApiClient
  methods, the Kiosk App over loopback via kiosk_inventory_sync_url — a
  new "Configure what starts the kiosk process" field), then POST each
  side's list to the OTHER side. Neither this module nor either receiving
  endpoint decides "who wins" — every row defends itself independently by
  its own updated_at, so the loop itself stays simple. No-op until an
  admin actually sets kiosk_inventory_sync_url, same convention as
  kiosk_start_command being empty meaning "nothing to supervise yet".
- A PIN set on a Local Kiosk User becomes a real login password at the
  kiosk terminal once synced (both sides hash with the same argon2
  scheme) — layered on top of kiosk_app's own badge/username-only
  default, never a replacement for it.
